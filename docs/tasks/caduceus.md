## 已冻结的产品规则

- 应用中文名为“双蛇杖”，英文内部标识暂用 `Caduceus`。
- 主菜单位置固定在“硬币决定器”之后、“提取部模拟”之前。
- 普通阶段共有九把武器；每次从本次尚未完成的武器中随机显示一把。
- 底部数字 1～9 与武器固定编号对应，数字本体为白色；完成后增加青色描边。
- 每把武器接受一种或多种基础动作；不同武器允许复用动作和音效。
- 六种应用专属基础动作是：横斩、竖斩、两个方向的斜斩、突刺、上挑。
- 只有侧键短按可以推进武器、推进“开始吧”和操作 Furioso；旋钮主按键短按不承担这些操作。
- 当前武器未完成时侧键短按无效；完成后侧键短按播放切换音效并切到剩余武器。
- 正确动作触发青色边框、对应武器音效和正确震动；错误动作触发红色边框和另一种震动，不播放对应武器音效，不改变数字状态。
- “第一次完成”的作用域是本次进入应用后、每把武器第一次完成；额外语音不跨退出保存。
- 普通阶段所有状态均不保存；退出再进入时重新开始。
- 第九把武器完成后，侧键短按显示“开始吧”；再次侧键短按进入 `Furioso`。
- Furioso 共九个节拍，最后一个节拍使用固定武器；前八个节拍的随机约束仍待确认。
- Furioso 成功完成后暂时不增加特殊结算内容；长按退出。
- Furioso 失败时使用失败震动并显示特殊武器；特殊武器的资源和后续细节仍待确认。
- 模式名称拼写固定为 `Furioso`。

## 不得破坏的架构边界

- `SysMotion` 继续作为 LSM6DSL 唯一采样所有者，统一使用 104Hz、±16g、±2000dps；正常和采集固件不得使用不同量程。
- 双蛇杖增加独立 `SysGestureProfile::Caduceus`；六种动作只在本应用内识别，不进入全局 Default。
- 识别层只产生基础动作语义、强度、方向和采样时间，不知道当前武器，不播放反馈，不绘制 UI。
- App 只根据武器配置表判断动作是否接受，不读取 IMU 原始值，不复制识别阈值。
- 只有被高置信度识别为六种基础动作之一的事件才可判错；普通晃动、模糊动作和被拒识的波形不能触发红框。
- `AppManager` 继续通过统一 `AppBase::onGesture()` 分发专属动作；不增加双蛇杖专用分发入口。
- 图片和音频由 SYS 资源域预热并持有；App 不直接打开 FATFS，也不持有文件路径。
- 音频继续通过 `AudioAssetId` 播放；复用音效时多个武器绑定同一个 ID，不重复加载 PCM。
- 正确、错误和 Furioso 失败震动通过 `sys_feedback` / `SysHaptic` 的业务语义封装；App 不写 TM6605 效果编号。
- 固定 UI 文本进入 `UIStrings`；绘制和动画进入 UI 层；App 只维护流程状态。
- 所有新代码写详细中文注释，新增或修改的串口信息使用中文；不确定的接口必须查声明、实现和调用点。

## 计划中的数据模型

```cpp
enum class CaduceusAction : uint8_t {
    HorizontalSlash,
    VerticalSlash,
    DiagonalSlashA,
    DiagonalSlashB,
    Thrust,
    Uppercut,
};

struct CaduceusWeaponPreset {
    WeaponId id;
    ImageAssetId image;
    AudioAssetId hitAudio;
    AudioAssetId firstClearVoice;
    uint8_t acceptedActionMask;
};

struct FuriosoBeat {
    WeaponId weapon;
    uint16_t cueDurationMs;
    uint16_t actionWindowMs;
    uint16_t gapDurationMs;
};
```

武器和动作保持多对多映射。实际枚举名、图片 ID 和音频 ID 必须根据最终资源表确定，不提前猜真实文件名。

## 计划中的应用状态机

```text
TeachingAwaitAction
  ├─ 正确 → TeachingSwitchReady
  └─ 错误 → TeachingAwaitAction

TeachingSwitchReady
  └─ 侧键短按 → 下一把未完成武器
                  └─ 九把完成 → AllClearedReady

AllClearedReady
  └─ 侧键短按 → StartPrompt（“开始吧”）
                      └─ 侧键短按 → FuriosoReady

FuriosoReady
  → FuriosoCue → FuriosoWindow
       ├─ 正确 → 下一个节拍/完成
       ├─ 错误 → FuriosoFailure
       └─ 超时 → FuriosoFailure

FuriosoFailure → SpecialWeapon → 等待长按退出
FuriosoComplete → 等待长按退出
```

当前武器正确后必须锁定动作输入，防止同一动作重复播放。Furioso 使用事件的 IMU 时间戳判断是否落入窗口，并在进入模式时一次生成九步节奏表，禁止每帧重新随机。

## 脱线 IMU 采集方案

脱线记录已经在原隔离测试体系中实现，不建立第二套传感器驱动：

1. 仍由 `SysMotion` 采样，不直接读取 BSP I2C。
2. 采集固件启动后由 ESP 独占挂载 FATFS，把 CSV 写入 `/Resources/_capture/imu/`。
3. 使用屏幕显示当前动作、倒计时、记录状态、重复次数和写入结果。
4. 使用旋钮选择动作标签；使用主按键启动一次记录；开始前留出倒计时，让用户松开按键并摆好姿势。
5. 每次记录保存为 `labelNN_sessionNNNN.csv`；CSV 前十一列保持旧契约，末尾增加会话号和三个 fresh 标志。
6. 完整会话先缓存在384KiB PSRAM，动作期间不刷新屏幕、不写FAT；结束后显示保存页并统一 write/flush/close。
7. 采集结束后关机或重启，进入独占 MSC 模式，再从电脑复制文件；ESP 写 FAT 与 PC MSC 绝不能同时进行。
8. 脱线模式验证稳定后再采六种动作，避免先采出无法区分重复次数或存在丢帧的数据。

采集数据至少覆盖：每类轻/中/重各 10～20 次、允许的不同握姿、其他五类动作互为负样本，以及菜单摇动、换武器、业力敲击、按键、普通手持、拿起放下、行走和近似未完成动作。

## 首批脱线数据检查

2026-07-28 已检查以下实机文件：

- `label10_session0002.csv`：正常手持，1870 个有效样本，约 19.97 秒；末尾包含一次明显大动作，不能直接作为纯静止基线。
- `label14_session0001.csv`：横斩，1404 个有效样本，约 14.96 秒；呈多轴联合运动，`gx/gy/gz` 均有明显参与，主轴会随挥动相位变化。
- `label15_session0001.csv`：竖斩，1398 个有效样本，约 14.96 秒；呈稳定的 `gz` 主导和正负回摆结构，与横斩已有明显可分性。

三份文件的序号均连续、时间戳不倒退，证明 PSRAM 整段缓存、FAT 落盘和 MSC 导出闭环有效。但当前仍有三项数据质量问题：

1. 新 CSV 在原十一列后增加了会话号和三个 fresh 标志；旧分析器要求恰好十一列，曾把新格式全部误报为无效。
2. 三份数据均约每 0.45 秒出现一次 30～40 ms 的周期空洞。底层源码确认 `USBCDC::availableForWrite()` 与 `flush()` 会分别按 `cdcTxTimeoutMs` 等待同一发送锁，默认 20 ms 可累计成约 40 ms；采集主循环每帧执行 `SysUsbMode::Service()`，时长与实测空洞吻合。
3. 横斩的 `ay`、竖斩的 `ax/ay` 已多次接近或达到有符号原始值上限，确认 ±8 g 发生削顶。

对应修正已经完成：

- `analyze-imu-capture.py` 同时接受旧 11 列和新 15 列，解析会话/fresh 字段；新文件从元数据读取量程，无元数据的旧文件固定按当时的 ±8 g 解释。
- `SysUsbSession` 只在隔离测试固件中把 CDC TX 锁等待设为 0 ms，继续运行原 `SysUsbMode::Service()`；普通固件仍保留 20 ms，不复制第二套 USB 服务。
- `SysMotion` 统一切到 104Hz、±16g、±2000dps，并新增只读 `SysMotion_GetAcquisitionConfig()` 供采集器写入频率/量程元数据。现有识别器和 Sea 均读取 BSP 换算后的物理量，不需要按比例修改阈值。
- 2026-07-28 构建通过：采集版 Flash 84.3% / RAM 54.5%，普通版 Flash 84.1% / RAM 54.5%。采样空洞消失和旧动作实机回归仍需烧录验证。

因此，首批数据只确认“横斩多轴联合、竖斩 `gz` 主导”这一可分方向；在采样空洞、量程和每类单会话问题解决前，不冻结窗口、阈值或判错规则。

## 第二批 ±16 g 数据检查

2026-07-28 使用新版固件检查 `label10/14/15_session0001.csv`：

- 正常手持：1858 样本 / 19.963 秒，无削顶；加速度最大约 4.49 g，合角速度峰值约 968 dps。
- 横斩：1393 样本 / 14.972 秒，无削顶；单轴加速度最大约 11.55 g，合加速度峰值约 12.34 g，合角速度峰值约 1786 dps，仍是 `gx/gy/gz` 多轴联合结构。
- 竖斩：1386 样本 / 14.946 秒，无削顶；`ax` 最低约 -11.83 g、`ay` 最高约 10.02 g，`gz` 约 -1186～1271 dps，继续稳定表现为 `gz` 主导。

三份文件均正确声明 104 Hz、±16 g、±2000 dps，序号连续、时间戳不倒退，陀螺仪每个保存样本均为 fresh。加速度约 6%～7% 样本不是 fresh，当前行沿用最近值；动作识别必须继续只让 fresh 陀螺仪推进陀螺仪相位。

但采样空洞并未随 CDC TX 超时清零而消失：

- 正常手持最大间隔 40.001 ms，48 次超过 15 ms，其中 44 次超过 30 ms。
- 横斩最大间隔 40.003 ms，37 次超过 15 ms，其中 32 次超过 30 ms。
- 竖斩最大间隔 40.001 ms，40 次超过 15 ms，其中 31 次超过 30 ms。
- 主空洞通常每 42～43 个样本出现一次，相邻约 450～460 ms，三份数据平均采样率约 93 Hz；与第一批基本一致。

因此，`USBCDC::availableForWrite()/flush()` 的 20 ms 锁等待不是唯一根因。Arduino-ESP32 的 TinyUSB 初始化还会创建 `configMAX_PRIORITIES - 1` 的 `usbd` 任务，即使主循环的 CDC 服务不再等待，也可能周期性抢占 Arduino loop。

第三版已经实现单变量对照：

- 采集固件未按侧键启动时，在 `USB.begin()` 前返回，不创建 TinyUSB `usbd` 任务；动作期间不再提供串口标签控制，只保留屏幕、旋钮、按键和 FAT 记录。
- `SysUsbMode::Service()` 在 USB 未启动时立即返回，正常固件与 MSC 启动成功后仍复用原服务。
- 按住侧键仍进入原独占 MSC；安全弹出后先把 FAT 交还 ESP，并复用 `SysFatUpdate::CheckAndApplyAtBoot()` 检查 `/Update`。有 `firmware.bin` 时可恢复普通固件；没有更新包时自动断开 USB 并重启到纯脱线记录状态。
- 采集版构建通过：Flash 84.3% / RAM 54.5%；普通版构建通过：Flash 84.1% / RAM 54.5%。真实采样节拍仍待 V4B 验证。

为继续缩小采集主循环的不确定耗时，第四版把记录路径进一步改成固定长度二进制样本池：

- `UpdateRecording()` 只从 `SysMotion` 缓存复制序号、时间戳、七个原始值和fresh位，不再逐帧执行 `vsnprintf` 或拼接可变长度CSV行。
- 384KiB PSRAM 现在是 `ImuCaptureRecord` 定长数组；记录结束、屏幕进入保存页后，才逐条格式化为原15列CSV并写入FAT，文件契约和现有分析器不变。
- 这次调整没有新增IMU读取任务，`SysMotion`仍是唯一采样所有者。若无USB第四版仍有约450ms周期空洞，应转查 `SysMotion`轮询节拍、LSM6DSL读取和主循环按键开销，而不能再归因于CSV实时格式化。
- 2026-07-28 构建通过：采集版 Flash 84.3%（1,768,377字节）/ RAM 54.5%（178,592字节）；普通版 Flash 84.1%（1,764,389字节）/ RAM 54.5%（178,448字节）。

## 第四版无USB、定长缓存实机检查

2026-07-28 检查 `label10_session0002.csv`：

- 1873个有效样本 / 19.967秒，实际平均采样率93.753Hz；序号连续、时间戳不倒退、无量程削顶。
- 1825个间隔为约10ms，3个约9ms，7个为30ms，37个为40ms；共44个间隔超过15ms，最大40ms。
- 大间隔之间通常相隔42～43个保存样本，即约450～460ms，周期结构与第二批数据一致；相比上一份正常手持约93Hz只有轻微波动，不构成问题改善。
- 陀螺仪每个保存样本均fresh；加速度111个样本非fresh，占5.93%，与上一批约6%～7%一致。

因此已实机排除 TinyUSB/CDC 和记录期 `vsnprintf`/CSV拼接是周期空洞的根因。按键状态机只读取GPIO和`millis()`，没有阻塞调用；当前仍不能仅凭源码断言是I2C还是任务调度。下一版应在固定记录中追加调用起点、`SysMotion_Update()`耗时和两次采集循环起点间隔：若调用耗时同步升至30～40ms，继续检查`Wire1`事务/任务抢占；若调用耗时正常而循环起点间隔拉长，则检查loopTask及显示TE等系统调度。未经这组对照，不创建高优先级第二采样任务。

## 资源与反馈计划

- 资源根目录暂定 `/Resources/caduceus/{images,audio}`，最终路径以真实资源清单为准。
- 图片优先统一为正方形 RGB565，以复用 `SysResourceIO::LoadSquareRgb565()`。
- 增加 `SysCaduceusResources` 作为应用资源域，由 `SysRes_Init()` 协调预热；进入 App 时不访问 FAT。
- 先统计所有 WAV 的格式、时长、单双声道、去重结果和 PCM 总量，再决定是否能全部常驻 PSRAM。
- `SysAudio` 当前只有六个 PCM Voice；Furioso 最小节拍间隔必须结合真实音效时长校验最大并发，不能假设无限叠音。

- “开始吧”优先复用 `UIPrescript::DecodeOverlayAnimator` 和当前解码动画风格，不复制文字刷新引擎。

## 进度更新规则
